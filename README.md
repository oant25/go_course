Trip Service

Сервис поездок TripGo — лабораторная работа 1 «HTTP API и PostgreSQL».

Умеет создавать поездку, отдавать её и завершать. Данные лежат в PostgreSQL, схема накатывается миграциями, создание и завершение поездки атомарно пишут в две таблицы. Конфигурация — только из переменных окружения, остановка по SIGINT/SIGTERM корректная.

Стек
Что	Чем
HTTP	net/http + роутер chi
Контракт	contracts/openapi/trip-service.openapi.yaml, код генерирует oapi-codegen
Валидация запросов	по тому же контракту, kin-openapi (nethttp-middleware)

oapi-codegen и goose подключены как tool-зависимости модуля (go tool ...), ставить их глобально не нужно.

Запуск

Нужны Go 1.25+ и tripgoctl.

bash
tripgoctl cluster start        # один раз на машину
tripgoctl environment start    # поднимает PostgreSQL и пишет его адрес в .env
make migrate                   # накатывает миграции
make run                       # запускает сервис

Makefile подхватывает переменные из .env.example (дефолты для локального запуска), а поверх них — из .env, который создаёт tripgoctl (там DATABASE_URL). Копировать и склеивать файлы руками не нужно.

Проверить, что сервис жив:

bash
curl -s localhost:8080/health   # {"status":"ok"}
curl -s localhost:8080/ready    # {"status":"ok"}, если база доступна

API

Источник истины — contracts/openapi/trip-service.openapi.yaml.

Метод	Путь	Ответы
POST	/api/v1/trips	201 + Location, 400, 409, 500
GET	/api/v1/trips/{tripId}	200, 400, 404, 500
POST	/api/v1/trips/{tripId}/finish	200, 400, 404, 409, 500

Ошибки ручек поездок — application/problem+json (RFC 9457) с полем code:

HTTP	code	Когда
400	invalid_request	тело не прошло валидацию по контракту или tripId не UUID
404	trip_not_found	поездки нет

Зависимости направлены в одну сторону: handler → service → postgres, и все они используют trip. trip ни от чего не зависит. pgx импортирует только пакет postgres.

Решения
Уровень изоляции: READ COMMITTED

Менеджер транзакций открывает транзакции с уровнем READ COMMITTED — это уровень PostgreSQL по умолчанию: каждый запрос видит данные, закоммиченные до его начала.

Его достаточно, потому что корректность наших операций держится не на уровне изоляции, а на атомарных проверках в самой базе:

запрет двух активных поездок — уникальный индекс (см. ниже), он работает на любом уровне изоляции;
запрет двойного завершения — условие status = 'active' прямо в UPDATE: второй параллельный UPDATE ждёт блокировку строки, после коммита первого перечитывает её свежую версию и ничего не обновляет.

REPEATABLE READ и SERIALIZABLE в тех же ситуациях вместо ожидания возвращали бы ошибку сериализации (40001), и пришлось бы писать повторы транзакций — без выигрыша в корректности для этих операций.

Менеджер транзакций

Интерфейс — Do(ctx, fn func(ctx) error) error (internal/postgres/tx.go).

Do открывает транзакцию, кладёт её в context под неэкспортируемым ключом и вызывает fn с этим контекстом.
fn вернула nil → COMMIT. Вернула ошибку → ROLLBACK, ошибка уходит наружу как есть (работает errors.Is). Паникнула → ROLLBACK, паника пробрасывается дальше и превращается в 500 в HTTP-слое.
Откат выполняется в контексте без отмены (context.WithoutCancel): если клиент оборвал запрос, ROLLBACK всё равно дойдёт до базы.
Репозиторий получает исполнителя через executorFrom(ctx, pool): есть транзакция в контексте — запрос идёт через неё, нет — через пул. Транзакция никогда не передаётся аргументом метода репозитория.
Вызов репозитория вне Do выполняется через пул: каждый запрос — отдельная автоматическая транзакция. Так работает GET /trips/{id}.
Вложенный Do видит транзакцию в контексте и новую не открывает: fn выполняется в той же транзакции, коммитом и откатом управляет внешний Do. Частичного отката (savepoint) у вложенного вызова нет.
Ключ контекста и executorFrom не экспортируются: положить транзакцию в контекст в обход Do снаружи пакета postgres нельзя.

Бизнес-код (internal/service) знает только интерфейс TxManager с одним методом и ничего не знает про pgx, пул и транзакции. Создание поездки — INSERT в trips и INSERT в trip_status_history внутри одного Do; завершение — UPDATE и INSERT в историю внутри одного Do. Если вторая вставка падает, в trips ничего не остаётся (проверено намеренной поломкой вставки в историю).

Запрет двух активных поездок у водителя

Частичный уникальный индекс в миграции 00001:

sql
CREATE UNIQUE INDEX trips_one_active_per_driver_idx
    ON trips (driver_id)
    WHERE status = 'active';
Уникальность driver_id проверяется только среди активных поездок; завершённых у водителя может быть сколько угодно, после finish он снова свободен.
Под конкурентной нагрузкой: второй одновременный INSERT находит в индексе незакоммиченную строку первого и ждёт исхода его транзакции. Первая закоммитилась — второй получает 23505 unique_violation; откатилась — второй вставляет успешно.
Репозиторий превращает 23505 в доменную ошибку trip.ErrDriverBusy (→ 409 driver_busy) только если ConstraintName — это наш индекс. Другие нарушения уникальности, например дубликат первичного ключа, остаются 500.
Проверка SELECT перед INSERT этого не обеспечила бы: оба параллельных запроса прошли бы проверку раньше, чем любой из них вставил строку.

20 одновременных запросов на одного водителя дают один 201 и девятнадцать 409.

Завершение поездки без гонки
sql
UPDATE trips SET status = 'completed', finished_at = $1, updated_at = $2
WHERE id = $3 AND status = 'active'
RETURNING ...

Проверка статуса и запись — одна атомарная операция, окна для параллельного запроса между ними нет; finished_at первой транзакции не перезаписывается. Если обновлено 0 строк, дочитываем поездку: её нет → 404 trip_not_found, есть → 409 trip_completed. 20 одновременных finish одной поездки дают один 200 и девятнадцать 409, в журнале ровно один переход active → completed.

/health и /ready
/health (liveness) отвечает 200, пока процесс жив, и в базу не ходит. Если бы ходил, при падении базы оркестратор перезапускал бы все инстансы по кругу, хотя перезапуск процесса базу не чинит.
/ready (readiness) пингует базу с таймаутом DATABASE_QUERY_TIMEOUT. Нет базы — 503: инстанс временно выводится из балансировки, но не перезапускается. База вернулась — снова 200 без перезапуска сервиса.
Валидация по контракту

Запросы проверяются middleware-валидатором по вшитому в бинарь OpenAPI-контракту до того, как попадают в хендлер: обязательные поля, additionalProperties: false (в том числе во вложенных объектах), диапазоны координат, price — целое >= 0, Content-Type. Правила не дублируются в Go: поменялся контракт — после make generate поменялась и валидация. Вручную проверяется только бизнес-правило «UUID не нулевой».

Graceful shutdown

По SIGINT/SIGTERM сервер перестаёт принимать новые соединения и ждёт текущие запросы не дольше SHUTDOWN_TIMEOUT (http.Server.Shutdown с дедлайном в контексте). Затем закрывается пул соединений с базой — строго после HTTP, чтобы дорабатывающие запросы не остались без соединений. Не уложились в таймаут — оставшиеся соединения закрываются принудительно, процесс завершается с кодом 1.

Деньги

Цена хранится в целых рублях (BIGINT), как требует контракт. Float для денег не используется.
